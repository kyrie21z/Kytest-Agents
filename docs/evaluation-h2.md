# Homework 2 评测结果

模型：百炼 `qwen3.7-flash`（OpenAI 兼容接口），四个角色共用。基准与指标定义见 [Design.md §7](../Design.md#7-基准为什么要新的以及它测什么)。
全部数字由 `bench/score.py` 执行各次运行产出的测试得到；原始记录在 [evidence/bench-dev1](evidence/bench-dev1/) 与 [evidence/bench-test1](evidence/bench-test1/)。

## 协议

1. 提示词只在开发集（5 题）上调整。
2. 冻结：提示词与基准资产固定在提交 `f12ad5e`，之后才第一次运行测试集（9 题）。测试集结果出来后没有再改提示词或资产。
3. 每题两种被测对象（`clean` 参考实现 / `buggy` 主缺陷），四种配置（`mas`、`no_planner`、`no_reviewer`、`single`）。
   开发集每格 1 次，测试集每格 2 次。
4. 区间是对运行做 bootstrap 的 95% 区间。样本小，只描述，不做显著性结论。

## 开发集：发现并修正的两个问题

开发集运行暴露的问题，以及对应的修改：

| 现象 | 根因 | 修改 |
|---|---|---|
| `qb_to_base` 两次运行都以 `forced` 结束：Reviewer 每轮都要求补“`num <= 0` 时抛 `ValueError`”的测试，还要求修改实现 | Planner 把 docstring 的前置条件（`num > 0`）当成了“会抛异常”的承诺；TestGen（H1 规则）正确地拒绝了没有异常承诺的 `pytest.raises`，于是 Reviewer 反复索要 | Planner：违反前置条件的输入属于未定义行为，列入 ambiguities；Reviewer：不得要求修改实现，不得要求规格未规定的行为（提交 `7795dd0`） |
| `bcb_bigram_counts` 有 bug 版：所有配置接受的测试都在参考实现上失败（“固化”） | 不是工作流的问题，是**基准的问题**：docstring 写着用 `itertools.permutations` 生成键（650 个，不含 `aa`），主缺陷“不含双字母”恰好可以由规格推出。只看规格的 Planner 两次都规划了 650 个键 | 逐个对照 docstring 审核全部 14 题的 36 个缺陷；6 个规格未规定的缺陷标为 `spec_decided: false`，不计入检出率、不能当主缺陷；该题改为 T5 并换成由示例决定的主缺陷（提交 `f12ad5e`）。受影响的 4 个开发集运行已重跑 |

第二个问题说明“合法替代实现 / 规格是否规定”这一层是必要的：规格本身自相矛盾时，“预期值来自规格”与“预期值来自实现”不能简单地用参考实现判对错。

## 开发集结果（40 次运行，每格 1 次）

被测对象为参考实现：

| 配置 | 测试数 | 缺陷检出率 | 误报率（合法替代实现） |
|---|---|---|---|
| mas | 9.0 | 100% | 0% |
| no_planner | 7.0 | 90% | 0% |
| no_reviewer | 8.0 | 70% | 0% |
| single | 7.0 | 90% | 0% |

被测对象为主缺陷：

| 配置 | 报告出缺陷 | 固化（bug 写进预期值） | 错误报告数 |
|---|---|---|---|
| mas | 5/5 | 0/5 | 0.2 |
| no_planner | 3/5 | 2/5 | 0.2 |
| no_reviewer | 0/5 | 0/5 | 0 |
| single | 0/5 | 1/5 | 0 |

成本：每次运行平均 `mas` 201 秒 / 7.4 万 token，`single` 86 秒 / 3.9 万 token。

没有 Reviewer 的配置按设计不能报告缺陷。它们“不固化”多半是因为按规格写的正确测试在有 bug 的实现上失败后被丢弃了：
bug 没有写进测试，但也没人发现。`bcb_bigram_counts` 有 bug 版上的 `no_reviewer` 是极端例子，6 个测试全部失败、被丢弃，最终 0 个测试（`failed`）。

## 测试集结果（144 次运行，9 题 × 2 种被测对象 × 4 种配置 × 2 次）

被测对象为参考实现（每配置 18 次）：

| 配置 | 测试数 | 缺陷检出率 | 误报率（合法替代实现） | 错误缺陷报告 |
|---|---|---|---|---|
| mas | 9.2 | 81% [65%, 96%] | 19% [3%, 39%] | 0.0 |
| no_planner | 7.6 | 76% [60%, 90%] | 14% [0%, 31%] | 0.2 |
| no_reviewer | 9.1 | 80% [64%, 93%] | 6% [0%, 17%] | 0.0 |
| single | 7.9 | 80% [67%, 92%] | 22% [6%, 44%] | 0.0 |

被测对象为主缺陷（每配置 18 次）：

| 配置 | 报告出缺陷 | 固化（bug 写进预期值） | 报告且同时固化 | 错误报告数 |
|---|---|---|---|---|
| mas | **16/18** | **0/18** | 0 | 0.1 |
| no_planner | 15/18 | 12/18 | 9 | 0.0 |
| no_reviewer | 0/18 | **0/18** | 0 | 0.0 |
| single | 0/18 | 10/18 | 0 | 0.0 |

成本（每次运行平均）：mas 252 秒 / 9.1 万 token / 12.7 次调用；single 119 秒 / 4.4 万 token / 6.6 次调用。
运行状态：mas 30 次 accepted、5 次 forced、1 次 failed（`ce_warehouse` 干净版 r1：TestGen 两次都用完轮数没有交出测试，按 0 个测试计入，未重跑）。

### 结论（只描述这 9 题、这个模型）

1. **Planner 消除了预期值污染。** 有 Planner 的两种配置在 36 次有 bug 的运行中一次都没有把 bug 写进测试；
   没有 Planner 的两种配置 22/36 次固化。这是全部结果里差距最大、区间不重叠的一项，直接支持“预期值先从规格推出”的设计。
2. **Reviewer 让缺陷被报告出来。** 没有 Reviewer 时，正确测试在有 bug 的实现上失败后被丢弃，缺陷无人发现（`no_reviewer` 0 固化但也 0 报告）。
   只有 Planner 与 Reviewer 同时存在时，才既不固化又能报告（mas 16/18）；`no_planner` 虽然也常报告，但 12/18 的接受测试同时固化了 bug，给出互相矛盾的信号。
3. **被测代码正确时，MAS 没有带来更强的测试。** 四种配置的缺陷检出率都在 76%–81%，区间大幅重叠。新增节点的价值在“实现有错时”而不在“实现正确时”。
4. **过度约束四种配置都有，差异不能下结论。** 误报全部来自 5 个合法替代实现，都是真实的过度约束：
   断言 `create_order`/`transfer` 返回 `None`（规格没说返回值），断言价格格式 `'$1.5'`（规格只给了 `$1.25`），断言内部连续空白保持原样。
   这些预期值来自实现的偶然行为。mas（19%）高于 no_reviewer（6%），可能与 Reviewer 要求补测试有关，但区间重叠，样本不足以判断。
5. **代价约为单 Agent 的 2 倍**（token 2.1 倍、时间 2.1 倍）。

### 过程记录

- 评分器修正：`qb_find_first_in_sorted` 的上游缺陷会让函数死循环，整次 pytest 超时、没有逐条结果，评分器起初把这些疑似缺陷测试记成“错误报告”。
  修正为：整次超时时逐条单独运行，挂起算失败（`tests/test_bench.py` 有对应测试）。对开发集与测试集都重新评分；只有“报告出缺陷”一列变化
  （mas 78%→89%，no_planner 72%→83%），被测对象为参考实现的指标不变。
- 测试集运行中途为提高并发重启过一次 runner：被中断的 5 次运行删除后从头重跑，其余已完成的运行保留。这次重启与结果无关。
