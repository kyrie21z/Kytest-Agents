# Homework 2 评测结果

模型：百炼 `qwen3.7-flash`（OpenAI 兼容接口），四个角色共用。基准与指标定义见 [Design.md §7](../Design.md#7-基准为什么要新的以及它测什么)。
全部数字由 `bench/score.py` 执行各次运行产出的测试得到；原始记录在 [evidence/bench-dev1](evidence/bench-dev1/) 与 [evidence/bench-test1](evidence/bench-test1/)。

## 协议

1. 提示词只在开发集（5 题）上调整。
2. 冻结：提示词与基准资产固定在提交 `f12ad5e`，之后才第一次运行测试集（9 题）。测试集结果出来后没有再改提示词或资产。
3. 每题两种被测对象（`clean` 参考实现 / `buggy` 主缺陷），四种配置（`mas`、`no_planner`、`no_reviewer`、`single`）。
   开发集每格 1 次，测试集每格 2 次。
4. 区间是对运行做 bootstrap 的 95% 区间。样本小，只描述，不做显著性结论。

## 开发集：发现并修正的两个问题

开发集运行暴露的问题，以及对应的修改：

| 现象 | 根因 | 修改 |
|---|---|---|
| `qb_to_base` 两次运行都以 `forced` 结束：Reviewer 每轮都要求补“`num <= 0` 时抛 `ValueError`”的测试，还要求修改实现 | Planner 把 docstring 的前置条件（`num > 0`）当成了“会抛异常”的承诺；TestGen（H1 规则）正确地拒绝了没有异常承诺的 `pytest.raises`，于是 Reviewer 反复索要 | Planner：违反前置条件的输入属于未定义行为，列入 ambiguities；Reviewer：不得要求修改实现，不得要求规格未规定的行为（提交 `7795dd0`） |
| `bcb_bigram_counts` 有 bug 版：所有配置接受的测试都在参考实现上失败（“固化”） | 不是工作流的问题，是**基准的问题**：docstring 写着用 `itertools.permutations` 生成键（650 个，不含 `aa`），主缺陷“不含双字母”恰好可以由规格推出。只看规格的 Planner 两次都规划了 650 个键 | 逐个对照 docstring 审核全部 14 题的 36 个缺陷；6 个规格未规定的缺陷标为 `spec_decided: false`，不计入检出率、不能当主缺陷；该题改为 T5 并换成由示例决定的主缺陷（提交 `f12ad5e`）。受影响的 4 个开发集运行已重跑 |

第二个问题说明“合法替代实现 / 规格是否规定”这一层是必要的：规格本身自相矛盾时，“预期值来自规格”与“预期值来自实现”不能简单地用参考实现判对错。

## 开发集结果（40 次运行，每格 1 次）

被测对象为参考实现：

| 配置 | 测试数 | 缺陷检出率 | 误报率（合法替代实现） |
|---|---|---|---|
| mas | 9.0 | 100% | 0% |
| no_planner | 7.0 | 90% | 0% |
| no_reviewer | 8.0 | 70% | 0% |
| single | 7.0 | 90% | 0% |

被测对象为主缺陷：

| 配置 | 报告出缺陷 | 固化（bug 写进预期值） | 错误报告数 |
|---|---|---|---|
| mas | 5/5 | 0/5 | 0.2 |
| no_planner | 3/5 | 2/5 | 0.2 |
| no_reviewer | 0/5 | 0/5 | 0 |
| single | 0/5 | 1/5 | 0 |

成本：每次运行平均 `mas` 201 秒 / 7.4 万 token，`single` 86 秒 / 3.9 万 token。

没有 Reviewer 的配置按设计不能报告缺陷。它们“不固化”多半是因为按规格写的正确测试在有 bug 的实现上失败后被丢弃了：
bug 没有写进测试，但也没人发现。`bcb_bigram_counts` 有 bug 版上的 `no_reviewer` 是极端例子，6 个测试全部失败、被丢弃，最终 0 个测试（`failed`）。
